# Install

## Requirements

| Tool | Needed for | If missing |
|---|---|---|
| `git` | everything | hard failure |
| `bash` 3.2+ | everything | hard failure |
| `jq` | reading the module registry | hard failure |
| `gh` (authenticated) | bootstrap's label and remote phases | those phases skip with a warning |
| `gh-sub-issue` extension | CCPM's real issue hierarchies | CCPM falls back to task lists |

```bash
# macOS
brew install jq gh
gh auth login
gh extension install yahsan2/gh-sub-issue

# Debian / Ubuntu
sudo apt-get install -y jq
# gh: https://github.com/cli/cli/blob/trunk/docs/install_linux.md
```

`agent-ops doctor` reports on all of these.

## Adding to an existing repository

```bash
cd your-repo
git submodule add https://github.com/PackMaaan/agent-ops .agent-ops
git submodule update --init --recursive
.agent-ops/bin/agent-ops install
.agent-ops/bin/agent-ops doctor
```

Commit the result:

```bash
git add .gitmodules .agent-ops AGENTS.md CLAUDE.md
git commit -m "chore: add agent-ops"
```

The generated symlinks under `.claude/skills/` are added to `.git/info/exclude`
and stay out of the commit — they are regenerated by `install` on every machine.

### What install does

1. Initialises any module that is not checked out.
2. Symlinks each enabled module's skill into `.claude/skills/`.
3. Writes a managed block into `AGENTS.md` and `CLAUDE.md` listing what is now
   available. Content outside the `<!-- BEGIN/END agent-ops -->` markers is
   preserved exactly.
4. Excludes the generated links from `git status`.

It is idempotent. Re-run it after any `git pull` that moves a submodule pointer.

### Telling collaborators

This is the one thing worth putting in your own README, because a plain
`git clone` gets submodule pointers but not their content:

```bash
git clone --recurse-submodules <your-repo>

# or, after a plain clone
git submodule update --init --recursive
.agent-ops/bin/agent-ops install
```

## Standing up a brand-new repository

Order matters — branch protection references the default branch, so that branch
has to exist on the remote first.

```bash
mkdir my-project && cd my-project
git init -b main

git submodule add https://github.com/PackMaaan/agent-ops .agent-ops
git submodule update --init --recursive
.agent-ops/bin/agent-ops install

# Offline phase: render the standard files, no API calls
.agent-ops/bin/agent-ops bootstrap --files-only
# → fill in any {{PLACEHOLDER}} values it reports

git add -A && git commit -m "chore: bootstrap repository standards"
gh repo create my-project --public --source=. --remote=origin --push

# The branch ref now exists, so the remote phases can succeed
.agent-ops/bin/agent-ops bootstrap --labels-only
.agent-ops/bin/agent-ops bootstrap --remote-only

# After the first CI run, pin the required status checks to real names
bash .agent-ops/modules/github-project/skills/github-project/scripts/init-branch-protection.sh \
  OWNER/REPO --from-current-checks
```

That last step is separate deliberately. Required status check names must match
what your workflows actually produce, and that is unknowable until a run exists.
Pinning guessed names is the most common cause of permanently unmergeable PRs.

## Harness destinations

| Flag | Directory |
|---|---|
| `--harness claude` (default) | `.claude/skills/` |
| `--harness agents` | `.agents/skills/` |
| `--harness factory` | `.factory/skills/` |
| `--harness opencode` | `.opencode/skills/` |
| `--harness all` | all four |
| `--dest DIR` | anything you like, repeatable |

Flags are repeatable, so `--harness claude --harness factory` installs to both.

## Copy mode

```bash
agent-ops install --copy
```

Copies skill directories instead of symlinking. Use it only when you need to:

- a filesystem or sandbox that does not follow symlinks
- vendoring for an air-gapped build

Two consequences. Copies do not track submodule updates, so you must re-run
`install --copy` after every `module sync`. And copying the `github-project`
content creates a derivative work under CC-BY-SA-4.0 — read
[`NOTICE.md`](../NOTICE.md) first.

## Verifying

```bash
.agent-ops/bin/agent-ops doctor
```

Checks tooling, registry validity, `.gitmodules` agreement in both directions,
module checkout state and pinned SHAs, every declared skill's `SKILL.md`, and
which skills are linked into the host.

Exit code 0 means healthy; warnings (missing optional tooling, no origin remote)
do not fail it.

For the GitHub side, the `github-project` module ships its own audit:

```bash
bash .agent-ops/modules/github-project/skills/github-project/scripts/verify-github-project.sh .
```

## Uninstalling

```bash
agent-ops uninstall                          # symlinks and managed blocks
agent-ops uninstall --dest .vendored/skills  # a non-standard destination
agent-ops uninstall --purge                  # also remove --copy'd directories

git submodule deinit -f .agent-ops
git rm -f .agent-ops
rm -rf .git/modules/.agent-ops
```

`uninstall` removes only symlinks it owns and the content between its own
markers. Files that `bootstrap` generated are left alone — they are yours now.
