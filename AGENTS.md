# Agent instructions — agent-ops

You are working on **Agent Ops itself**, not on a repository that consumes it.
That distinction drives most of what follows.

## What this repository is

A composition layer. It owns almost no capability of its own; it makes other
people's Agent Skills installable, discoverable, and updatable as one unit. Two
modules are pinned as git submodules under `modules/`, and `skills/agent-ops/`
is the routing skill that decides which one is authoritative for a request.

Read [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) before making structural
changes.

## Hard rules

1. **Never edit anything under `modules/`.** Those are pinned submodules —
   upstream's code, checked out at a specific commit. Edits are lost on the next
   `agent-ops module sync`, invisible to other consumers, and turn future
   updates into conflicts. Fix it upstream, or add a new module.

2. **`.gitmodules` and `registry/modules.json` change together**, always via
   `agent-ops module add` / `agent-ops module remove`. They are two halves of
   one fact; CI fails on drift in either direction.

3. **bash 3.2 is the floor.** macOS ships it. Under `set -u`, `${#arr[@]}` on an
   empty array is a fatal error — use newline-delimited strings wherever a list
   can be empty. CI's macOS leg exists to catch this.

4. **Compose, do not duplicate.** Where the `github-project` module already
   ships an asset template or a script, render or delegate to it. Agent Ops
   supplies only what the modules do not cover. Reimplementing module behaviour
   is a bug, not a feature.

5. **Never auto-commit a submodule bump.** `module sync` prints the commit range
   and stops on purpose. That review is a security control.

## Layout

| Path | What lives there |
|---|---|
| `bin/agent-ops` | the single entry point; dispatches to `scripts/` |
| `scripts/lib/common.sh` | host detection, registry access, managed blocks, output |
| `scripts/install.sh` | symlink module skills into the host repo |
| `scripts/bootstrap-repo.sh` | apply GitHub standards to the host repo |
| `scripts/doctor.sh` | diagnose tooling, registry, checkout, install state |
| `scripts/module-*.sh` | registry lifecycle |
| `registry/modules.json` | the declarative inventory — single source of truth |
| `skills/agent-ops/` | the routing meta-skill and its references |
| `templates/github-standards/` | only what the modules do not already ship |
| `tests/` | bash assertions, no framework dependency |

## Working on it

```bash
make init      # check out the pinned modules
make test      # the full suite
make check     # version + schema + tests
make lint      # shellcheck, yamllint, markdownlint (if installed)
```

The suite drives the scripts with `--target` against throwaway repositories in
`mktemp`, so it exercises the **working tree**, not the last commit. Behaviour
changes need assertions; `tests/lib.sh` has the helpers.

## Shell conventions

Every script sources `scripts/lib/common.sh`, which sets `set -euo pipefail` and
provides `info` / `ok` / `skip` / `warn` / `fail` / `die` / `would`. Diagnostics
go to stderr; only machine-readable output goes to stdout.

Two `set -euo pipefail` traps that have already bitten this codebase:

- `grep` exits 1 on no match, which `pipefail` turns fatal — add `|| true`
- `[ test ] && action` propagates its status when it is the last statement in a
  function

Colour variables must be brace-delimited when adjacent to a multibyte glyph
(`"${C_GREEN}●${C_RESET}"`, never `"$C_GREEN●$C_RESET"`) — bash 3.2 absorbs the
UTF-8 bytes into the variable name.

## Skills in this repository

This repository is the *source* of these skills, so they are not symlinked here
the way they would be in a host repo. Read them at their real paths.

| Skill | Path | Authority for |
|---|---|---|
| `agent-ops` | `skills/agent-ops/` | Routing, bootstrap, module management |
| `ccpm` | `modules/ccpm/skill/ccpm/` | PRDs, epics, GitHub sync, parallel agents |
| `github-project` | `modules/github-project/skills/github-project/` | Branch protection, auto-merge, sub-issues |

A host repository gets a `<!-- BEGIN agent-ops (managed) -->` block here
instead, generated by `agent-ops install`. Do not add those markers to this
file — running `install` against a mis-detected host would then rewrite your
instructions.
